## Challenge

**The Vendor's Secret Door** (150 pts) asked for a vendor-only surface while the account I registered was only a buyer. The hint pointed at becoming a vendor somehow — without a normal upgrade path in the UI.

## Approach

1. Confirm identity in the app dashboard — account showed as a non-vendor buyer
2. Inspect cookies in Chrome DevTools → Application and find the `auth-token` cookie
3. Recognize the value as a JWT (three Base64url segments: header, payload, signature)
4. Decode the payload (CyberChef works well) and read the JSON claims, including role / vendor status
5. Change the role claim to vendor, re-encode the payload, and rebuild the token using the original header and signature
6. Replace the `auth-token` cookie with the edited value and reload

After reload, the vendor dashboard loaded and exposed the flag.

## Why this worked

A JWT is only trustworthy if the server **verifies the signature** (or uses an encrypted token) before honoring claims. Here the app apparently trusted the payload as-is. Keeping the original signature while rewriting claims is a classic sign that verification is missing or broken — the server never noticed the forgery.

In a real system, role changes belong on the server after a successful authorization check, not in cookie contents the browser can rewrite.

## Takeaways

- Treat client-held tokens as attacker-controlled input until signature verification is proven
- Decode JWTs early in web auth challenges — claims often encode role, admin, or subscription state
- DevTools Application / Storage tabs are enough to inspect and swap session cookies during a CTF
- The fix on the app side is verify-then-trust (and preferably keep authorization decisions server-side), not "hide" the vendor UI
